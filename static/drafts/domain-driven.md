# Domain Driven Development/Design
The one company I worked at that was obsessed with DDD left be feeling mixed about the model.

Traditionally, Domain Driven Development is the idea that your data models and even code (to some extent) should mirror the business. 

One of the reasons people love DDD is because it supposedly makes naming easier -- something I am a bit skeptical of. I am convinced naming things is never easy. George RR Martin seems to agree (at least about his fantasy characters).

> “Names are really hard. And I need to know the name of the character before I can begin to write about them.”

For me this really encompasses the problem. You cant code if you can't agree on the names or even structures for the format of that code because you are so caught up on business specifics. It also means a new developer now not has to only learn the tech stack but also the business before they can meaningfully contribute anything. The upside to this is easy to argue: "Well that is why DDD is good you see ... they get to do both and learn about the company."  Maybe ... and even if I hand that win it doesn't change the fact that when that application was created I bet quite a few new devs were in meetings where semantic questions were raised about which departments phrase something a certain way and whether to rename code that had already been created -- or code that now resides in several states.

I think the best way I would some up DDD is it forces you to question the data, which in my opinion is great -- it enforces validation. But it also can force paralysis, arguments that are utterly unneeded and 

It causes you to ask the right questions but doesn't grant you any extra time to answer them.
